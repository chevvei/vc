# 01 — 光栅化：把三角形涂满屏幕的流水线

## 一、故事导入：为什么是三角形

任何 3D 物体（人头、汽车、点云）都要先变成**三角形网格**才能进 GPU，因为：

1. **三角形是平面的最小单位**——3 点决定 1 个平面，4 点就可能扭曲（四边形不保证共面）
2. **硬件只为三角形造电路**——30 年优化，插值/剔除/光栅化全是三角形专用芯片
3. **数学最简**——重心坐标插值（下文）对三角形有闭式解

点云例外：点云跳过图元装配直接画点，所以 LidarAssistant 渲染百万点很轻松。

## 二、整条流水线：五个车间

```
顶点数组 ──→ ①顶点着色 ──→ ②图元装配 ──→ ③光栅化 ──→ ④片段着色 ──→ ⑤测试混合 ──→ 屏幕像素
  (GPU外)    (可编程)      (固定)        (固定)       (可编程)       (固定)
```

### ① 顶点着色（Vertex Shader，可编程）

每个顶点跑一遍你写的程序，干一件事：**MVP 变换**（见 00 篇）。
顺便把每个顶点的属性（法线、纹理坐标、颜色）变换好，传给下游。

### ② 图元装配（固定功能）

把每 3 个顶点拼成一个三角形。也在这里做"背面剔除"——法线朝里的三角形
（你看到盒子的内壁）直接扔掉，白省一半工作量。

### ③ 光栅化（Rasterizer，固定功能）—— 本篇主角

判断三角形覆盖了屏幕上哪些像素，把"3 个顶点的属性"变成"每个被覆盖
像素的属性"：

```
      v0 (红)                    ● 红红红红
     / \           光栅化         ● 红红红红红
    /   \          ─────→        ● 红红红红红红红
   v2────v1 (蓝)                 ● 红红红红红
                                 ● 红红红
```

**插值（varying）**：三角形内部某像素的颜色，按"重心坐标"在三个顶点间
加权平均——离红顶点越近越红。这个插值是**硬件电路**做的，零成本。

> 挂钩 CUDA：GPU 把 fragment 按 2×2 像素块（quad）打包调度，
> quad = 32 线程 warp 的"图形学出厂设置"。warp 这个概念就是为它发明的。

### ④ 片段着色（Fragment/Pixel Shader，可编程）

每个像素跑一遍你写的程序——算光照、采样纹理、算法线贴图。
**这是 GPU 算力的最大消耗者**（现代游戏 60%+ 时间在这里）。

### ⑤ 测试与混合（固定功能）

- **深度测试（Z-Buffer）**：每个像素记住"离我最近的物体深度"。新来的
  片段如果比记着的更远 → 丢弃；更近 → 覆盖并更新深度。
  > 神来之笔：不需要先画远的后画近的（画家算法），乱序画也对。
  > 代价：每像素 4 字节深度缓存（1080p = 8MB 显存）。
- **Alpha 混合**：半透明物体按 α 加权和已有颜色混合（玻璃、烟雾）。
  > 雷区：混合必须按**从远到近**排序，否则半透明会画错——这个排序
  > 约束在 3DGS 里变成主性能瓶颈（见 07 篇，同一个问题的高级形态）。

## 三、为什么快：为并行而生的流水线

每个三角形独立、每个像素独立 → 一帧百万三角形可以随便切给几万个线程。
GPU 的所有硬件设计（warp 调度、大规模线程、高带宽显存）都是为这个特征定制的。

具体数字体感（RTX 4090，~82 TFLOPS）：
- 1080p 屏幕 ≈ 200 万像素，每帧每像素约 100~1000 次浮点运算
- → 一帧 2~20 GFLOP，60fps 即 120~1200 GFLOP/s —— 只吃掉零头
- 剩下的算力全喂给** fragment shader 的复杂光照**（这就是为什么画面能越做越好：管线没变，shader 越写越狠）

## 四、为什么"假"：光照是算出来的，不是物理的

光栅化只算"三角形和像素的几何关系"，**不管光怎么传播**。于是：

| 物理现象 | 光栅化的伪造手法 | 破绽 |
|---|---|---|
| 阴影 | Shadow Map：先从光源视角"拍一张深度图"，画物体时对照 | 只能硬阴影，软阴影要多采样 |
| 反射 | 环境贴图（cubemap）：提前拍好四周全景图，按反射方向查表 | 镜子里看不到动态物体 |
| 全局光照 | 光照探针/baked lightmap：提前离线烘焙存贴图 | 动态光源全废 |
| 折射 | 直接忽略或简单扭曲 | 玻璃后面基本是贴图 |

这些技巧统称"** baking（烘焙）+ 采样预计算**"，本质是**用空间换真实**：
预先算好存起来，运行时查表。游戏 60fps 就是这么骗出来的。

## 五、什么场景用光栅化（决策）

用光栅化，当你的需求是：
- **实时**（≥30fps）交互渲染：游戏、CAD、数字孪生、**点云可视化**
- 真实感要求"够用就行"，可以接受烘焙/贴图技巧
- 物体是显式网格/点集（有明确的三角形列表）

不用光栅化，当：
- 需要物理正确的反射/折射/焦散 → 光线追踪（02）
- 场景是"照片重建"的隐式表示 → NeRF/3DGS（07）

## 六、面试讲法（30 秒版）

> 光栅化是"物体到屏幕"的正向投影：顶点经 MVP 变换后，硬件把三角形
> 光栅化成像素集，属性按重心坐标硬件插值，每个像素跑 fragment shader
> 算光照，最后 Z-Buffer 解决遮挡。它的优势是每个像素天然独立、极度
> 并行，是 GPU 架构的原始设计目标；代价是光照不物理——阴影反射全靠
> shadow map、环境贴图这类预计算技巧伪造。所以它是"实时"和"真实感"
> 之间的经典折中，实时光追普及前是游戏唯一选择。

## 七、自检问答

1. **Q: Z-Buffer 为什么能解决遮挡，代价是什么？**
   A: 每像素存最近深度，乱序绘制也正确；代价 4B/像素显存 + 深度读写带宽。
2. **Q: 画家算法和 Z-Buffer 的本质区别？**
   A: 画家算法按序绘制（排序成本、循环遮挡无解）；Z-Buffer 逐像素贪心（无序容忍，并行友好）。
3. **Q: 光栅化管线哪两步可编程？各跑多少次？**
   A: Vertex shader 每顶点一次（做 MVP），fragment shader 每像素一次（算光照纹理）。
4. **Q: 为什么点云渲染比三角网格轻松？**
   A: 跳过图元装配和光栅化插值，一个点画一个像素，纯 fragment 吞吐问题。
