## 关键机制

（3-5 条，每条一句话，可配伪代码）

SMEM Bank 的硬件寻址规则


Ampere/Turing GPU：

- SMEM 一共 **32 个 bank**，编号 0~31。
- 硬件规则：**把字节地址右移 2 位，然后取低 5bit，得到 bank 编号**


```
bank_id = (byte_addr >> 2) & 0x1F
```


`>>2`：除以 4；`&0x1F`：取最后 5bit，范围 0~31。


硬件设计： **每个 bank，最小寻址单元是 4 字节（一个 32bit 字）** 。
bank 不关心字节内部的 0~3 号字节，它一次拿 4 字节。所以硬件会先把字节地址按 4 字节对齐，再分配 bank。



> 硬件设计： **每个 bank，最小寻址单元是 4 字节（一个 32bit 字）** 。
> bank 不关心字节内部的 0~3 号字节，它一次拿 4 字节。所以硬件会先把字节地址按 4 字节对齐，再分配 bank。

举例：
字节地址 0 → 0>>2=0 → bank0
字节地址 4 → 4>>2=1 → bank1
字节地址 8 → 8>>2=2 → bank2
字节地址 12 →12>>2=3 → bank3


……
字节地址 124 →124>>2=31 → bank31
字节地址 128 →128>>2=32 → 32 & 0x1F = 0 → bank0
👉 每 4 字节，bank 编号 + 1；32 个 bank 一轮循环。

> 想象：32 个收银台，每个收银台负责一串连续的 4 字节块：
> bank0：0~3，128~131，256~259 ...
> bank1：4~7，132~135 ...
> bank2：8~11 ...




## 2. 代入 float：1 个 float = 4 字节

数组：`__shared__ float buf[];`

- `buf[idx]`：第 idx 个 float 元素
- 这个元素的**起始字节地址 byte_addr = idx × 4**

把 byte_addr 代入硬件 bank 公式：




```
bank_id = (byte_addr >> 2) & 0x1F
        = ( (idx × 4) >> 2 ) & 0x1F
```



`×4` 和 `>>2` 刚好抵消！
`idx * 4 >> 2 = idx`    注意 >> 2 即除以4



```
bank_id = idx & 0x1F = idx & 31
```



✅ 这就是简化公式的来源！
**只有元素是 4 字节类型（float,int,uint32_t）的时候，这个简化公式才成立！**


重点坑：如果你不是 4 字节类型，这个简化就失效！
比如 `__shared__ double buf[]`，double 占 8 字节：
byte_addr = idx ×8
bank_id = (idx*8 >>2)&31 = (idx*2)&31
bank_id = (idx*2) &31， **不再是 idx&31** ！



## 回到之前经典坑：线程 i 访问 buf [i*32]（float 数组）

`buf[i*32]`，数组下标 idx = i*32
bank_id = idx & 31 = (i*32)&31
32 的二进制：`100000`，`31` 是 `011111`。
`32 & 31 = 0`，所以不管 i 等于多少，bank_id=0。
所有线程全部命中 bank0，32-way bank conflict。完美对应我们前面收银台故事。


字节地址视角再看一遍：
`buf[i*32]` 的字节地址 = i*32*4 = i*128
bank_id = (128*i >>2)&31 = (32*i)&31 = 0。
两种计算方式结果一致。

## 5. 一个极易混淆的点：为什么硬件这么设计？

为什么 bank 按**4 字节字**来分配，而不是按字节分配？

1. GPU 的 SMEM 是 32bit 宽的 SRAM 阵列，bank 硬件端口是 32bit；一次读写最小粒度就是 32bit（4 字节），硬件不支持单独读写 1 字节。
2. 32 个 bank，每个 bank 32bit 位宽。一次并行访问，理论带宽：32 × 4B =128B per cycle。
3. 这种交织（interleaved）地址映射，是 SRAM 多 bank 阵列的经典布局：**地址连续的字分到不同 bank，最大化连续访问的并行带宽**。
   正常顺序遍历 buf [0],buf [1],buf [2]…，落在不同 bank，全并行无冲突。这是硬件设计者想要的最优访问模式。
   代价就是：如果你跨步是 32，全部落到同一个 bank，性能暴跌。

## 4. 用收银台类比重新理解这套寻址

硬件规则：

- 把 SMEM 内存切成连续的 4 字节小包裹。
- 包裹 0 → 收银台 0；包裹 1 →收银台 1；包裹 2→收银台 2… 包裹 31→收银台 31；包裹 32→收银台 0 循环。

float 刚好占一个 4 字节包裹。
`buf[0]` → 包裹 0 → bank0
`buf[1]` → 包裹 1 → bank1
`buf[31]` →包裹 31 →bank31
`buf[32]` →包裹 32 →bank0

所以：**float 数组下标 = 包裹编号**，直接 `idx &31` 就是收银台号。

> 如果是 double（8 字节，占 2 个包裹）
> `buf[0]` →包裹 0+1 →bank0
> `buf[1]` →包裹 2+3 →bank2
> `buf[2]` →包裹 4+5 →bank4
> bank_id = idx*2 &31，步长变成 2。

`__shared__ float buf[1024];`

# 浓缩总结（面试背诵版）

1. SMEM 硬件寻址看**字节地址**，原生公式：`bank_id = (byte_addr >> 2) & 0x1F`。
   原理：每个 bank 最小访问粒度是 4 字节 (32bit)，硬件先把字节地址转为 4 字节字地址，再 mod32 分配 bank。
2. float 占 4 字节，`byte_addr = idx *4`，代入公式后`*4`和`>>2`抵消，简化为`bank_id = idx & 31`。
3. 简化公式**只对 4 字节类型 (float/int) 有效**，8 字节 double 要重新推导。
4. 硬件设计初衷：连续数组元素落在不同 bank，顺序访问最大化并行带宽；跨步等于 32 会触发最坏 32-way 冲突。



## **验证：**

`0x1F` 是十六进制，等于十进制 **31**
二进制：`0x1F = 11111`（5 个 1）


`32` 十进制，二进制：`100000`

> `&` 是 **按位与运算** ：每一位，两个都是 1 结果才是 1，否则 0。对齐最低位：



```
    32 → 1 00000
  0x1F → 0 11111
    & -----------
          0 00000
```


所以 `32 & 0x1F = 0`

## 再验证几个同类数字（方便理解 bank 计算）

- 33 → `100001` & `011111` = `000001` → 1
- 64 → `1000000` & `0011111` = 0
- 65 → `1000001` & `0011111` = 1


### 本质含义：`& 0x1F` = 取数字的**最低 5bit**

`0x1F` 的掩码只有低 5 位是 1，高于第 5 位的 bit 全部被清零。

- 32 = 2⁵，二进制 1 在第 6 位，低 5 位全 0 → `&0x1F`结果 = 0
- 64=2⁶，1 在第 7 位，低 5 位也是 0 → 结果 = 0

回到我们 bank 冲突例子：
`idx = i * 32`
不管 i=0,1,2,3…
`idx & 0x1F = (i*32) & 0x1F = 0`
所有线程拿到的 bank_id 都是 0，全部挤到 bank0，32-way 冲突。
